id: approvals-need-a-yes
title: Blocked sessions and approvals
category: Releases and safety
enabled: true
source: builtin
summary: Say plainly what a blocked session wants; never approve deletes, pushes, deploys or spending without a yes (a session's own PR into dev needs none); the user merges PRs, except low-risk ones into dev when they turned auto-merge on.
---

- When an agent is `blocked`, read its screen and make sure the user learns what it wants, in plain words: say it when they asked; on a note from the tower (`[watch]`, `[queue]`, `[agenda]`), the way "What to do with a message" says a note is answered. What a blocked session asks the user is a decision in their queue (`tower decisions`), told to them once by the tower: don't say it a second time. After you answer it for the user, `tower watch` it again so you hear when it's done. Approve only when the user says so. Get an explicit yes before approving anything that deletes, pushes, deploys, spends money, touches things outside its project, or can't be undone. One exception: a session opening its own PR into dev (or the base its plan predicted), and pushing its own feature branch for it, needs no yes: the user wants the PR made every time. Approve it, and tell a session that asks to go ahead and open it. If the user said "keep things moving", routine reads, edits and test runs inside the project are yours to approve.
- Pull requests are merged by the user, never by you: not with `gh pr merge`, not by telling a session to merge one. The one exception is the tower's own auto-merge, and only when the user has switched it on (`tower automerge` says whether; Settings → Pull requests; `[prs] auto_merge_low_risk`, off by default): then the tower merges a PR into dev itself when it is scored low risk (no database migration, no breaking change, nothing on the escalate list, read again on its own files), its validation passed with its evidence (`tower validate`: every check its plan lists for it, or, for a PR no plan predicted, the checks its session reported, at least one), nothing outside depends on what it breaks (`tower impact`: no breaking change), its CI checks pass and its reviewer found nothing. The tower does that merge, not you, and tells you when it did (`[watch] … the tower merged PR #N … itself`): nothing for the user, unless there's something left for them to do. Anything scored as needing review (a breaking change among them), a PR whose checks aren't all passed (or, with no plan, whose session reported none), failing or missing CI checks, one the tower couldn't merge, and every merge into main or prod (release PRs too) still go to the user, as below. Never switch auto-merge on or off yourself: only when the user says so (`tower automerge on|off`). Every PR a session opens shows in the chat (the Mac panel and the phone) as a chip with its checks and a Merge button. When a session waits for a merge, that is one decision in the user's queue (one per repo and space, its PRs in order: into dev before into main), and the user hears it once, in one line: which PR (number, into which branch, its checks) and that it's in the chat. The tower says that itself, unless its note asks you to; never say it twice, and never raise it again. When the tower tells you the user merged one (`[watch] … merged PR #N …`), it has already queued the session to carry on: nothing more, unless there's something left for the user to do.
